### Q4–Q8. Could the bridges work outside Blueprint, with gRPC interceptors and no application changes?
**Yes, for Go gRPC services. No application logic, RPC schemas, or manual instrumentation code change.**

**What Blueprint's generated wrappers do today** (`plugins/opentelemetry/ir_ot_client.go`, `ir_ot_server.go`):
- **Forward carrier:** an extra RPC argument carrying the trace context, plus `_br` baggage from the SDK wire table.
- **Return carrier:** an extra `retCtx` return value.
  - On the client span: `PrepareCheckpoint`, then `AddToMerge`.
  - On the server span: `MergedChildren`, then `PrepareCheckpoint`.
- **Child accounting:** `childCount`, the per-child start ordinal (`__seq`), and the end-order list for SB's `remEndEvents`.

**What already lives outside Blueprint:** the SDK processors, the reverse-checkpoint policy, the priority exporter with HP retry, config discovery, and the collector components.

**The interceptor mapping:**

| Wrapper job | Interceptor equivalent |
|---|---|
| Forward carrier | Request metadata: OTel propagator plus `_br` under a `-bin` key |
| Return carrier | Response trailers. The server interceptor, after `handler()`: count children, `remEndEvents`, merge, `PrepareCheckpoint`, `grpc.SetTrailer`, then End the span. The client interceptor: `grpc.Trailer()`, `PrepareCheckpoint`, then merge into the parent's state held in `ctx`. |

**Q5, without client spans:** child counting and ordinals must live in the **client interceptor**, not a SpanProcessor. The child's first span starts in a different process, so the parent's SDK never sees a local `OnStart`. Both jobs are call-site events anyway: the ordinal goes out in metadata before the request is sent, and the end order is recorded at completion.

**Q6, can the client interceptor exist without creating a client span?** Yes. It works from the parent server span: `trace.SpanFromContext(ctx)` for the parent context and the server span's wire state for `_br`. It can keep:
- **Depth numbering:** write a "virtual" +1 level into `_br`, so today's cpd 2..4 and 2..6 remain valid. A checkpoint scheduled on a virtual level needs a rule, such as promoting it to the callee's server span. The alternative is counting hops and halving cpd.
- **Return-path routing:** run the per-hop trial against the live parent server span. Emission then lands on the server span's record.
- **Caveat:** today PB's depth counts client *and* server spans (`pb_processor.go:491`, parent depth + 1), so one RPC hop is two depth levels.

**Q7 and Q8, no application changes:** application code and schemas are untouched. What's needed:
- One install point: TracerProvider plus interceptor options at startup, the same surface as standard OTel. Zero source changes in Go would need compile-time injection.
- The usual `ctx` propagation. Where the app drops `ctx`, the truss terminates locally instead.
- Hooks on every edge that should carry trusses: gRPC interceptors, and HTTP middleware plus a RoundTripper. Asynchronous edges terminate locally by design.
- Proxies must pass metadata and trailers.

Developers write no instrumentation code. Other corner cases:
- Retries and hedged requests need per-attempt hooks (`stats.Handler`) or retries turned off, or two attempts share one ordinal.
- Calls made after the handler returns should tell the callee to terminate locally.
- A client that abandons a call loses the trailer, so the callee should terminate locally when its `ctx` is done. The current Blueprint client template has the same gap: an RPC error leaves `retCtx` empty.

## 2. Earlier questions (before this session's context window)

- **Can reverse trusses pass through cpd-scheduled checkpoints?** Originally no: a scheduled checkpoint terminated every returned truss. The user asked for a switch, which was implemented as the discovery key `reverse_passthrough`:

  - Tests are in `reverse_passthrough_test.go`.
  - Set it per run with `derive_dsb_sn_nw.py --reverse-passthrough`.
- **"What is this leak?" / "I thought Go didn't have memory leaks":** the refused-trace census in `runtime/plugins/otelcol/refused_ids.go` kept a global map plus an append-only slice that were never freed. That's a logical leak through retained references. The live heap grew 82 → 302 → 544 → 931 MB over overloaded tails; with GOMEMLIMIT at 1 GiB and GOGC=off, that meant a GC death spiral, which contaminated back-to-back passes.
  - **Fix:** a bounded dedup window (5 s, 64k cap) and the census **off by default** (`RETCTX_REFUSED_CENSUS=on` to enable). Tests are in `refused_ids_test.go`.
  - **Policy:** the user said no census in performance runs; loss evaluation is a separate experiment.
- **"How is it that untraced SN is so much worse?"** Deployment variance: the database CPU per request is identical across kinds (about 3.6–4.6 ms on usertimeline-db).

- **"Does SB with passthrough look similar to previous runs?"** Same throughput, LP curve and HP = 0. At n=1 its knee p99 was 10–50% higher.
